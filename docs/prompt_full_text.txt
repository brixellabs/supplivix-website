4. Phase 2: API, COD, free shipping and discount tokens
Prompt to agent
Build the REST API under /api/v1/ with DRF. Use serializers for all validation, pagination (20 per page), filtering and ordering on the product list, and a consistent error format { "code": "...", "message": "...", "fields": { "field": ["msg"] } }.

COD rules
payment_method is always COD. Reject any other value.
Guests may order with name, phone, email and address. Logged-in users can pick a saved address.
Stock is decremented inside a database transaction using select_for_update(). If stock is insufficient the order fails with a clear message and nothing is written.
The order confirmation page and email show: order number, items, totals, "Pay Rs. X in cash on delivery", and the delivery address.
Phone validation accepts Pakistani mobile formats 03XXXXXXXXX and +923XXXXXXXXX and stores them normalized.
Free shipping rule
Assumption to confirm with the client: free shipping applies when the cart subtotal after discount is Rs. 2,000 or more. Otherwise a flat fee applies (default Rs. 200). Both values live in SiteSetting (free_shipping_threshold, flat_shipping_fee) and are editable from the admin dashboard. The cart and checkout show a progress message such as "Add Rs. 450 more for free shipping".
Discount token (coupon) rules
Codes are case-insensitive, stored uppercase, 4 to 20 characters, letters and digits only.
Types: percentage or fixed amount. A percentage coupon can have a maximum discount cap.
Optional minimum order amount, start and end date, active flag, optional category restriction.
Limits: total uses and uses per user (or per email for guests).
One coupon per order. A coupon can stack with free shipping.
Discount never makes the total negative and is never applied to the shipping fee.
Redemption is recorded inside the same transaction as the order. Two simultaneous orders must not exceed the usage limit (use select_for_update() on the coupon row).
Error messages are specific: "This code has expired", "Minimum order of Rs. 1,500 required", "You have already used this code", "This code is not valid for the items in your cart".
Totals are always recomputed on the server. Never trust prices or discounts sent by the client.
Totals formula
\text{grand total} = \text{subtotal} - \text{discount} + \text{shipping}, \quad \text{shipping} = \begin{cases} 0 & \text{if } \text{subtotal} - \text{discount} \ge T \\ F & \text{otherwise} \end{cases}
T is the free shipping threshold and F is the flat fee.
Acceptance: every endpoint has pytest tests for success, validation failure, permission failure and edge cases listed in Phase 9. Throttling is on for auth, coupon and order endpoints.

8. Phase 6: SEO and AEO
SEO is search engine optimization. AEO is answer engine optimization: making the content easy for AI assistants and featured snippets to quote correctly.
Rendering decision (important)
A plain client-side React app sends crawlers an empty page. To keep React as required, do both of the following:
Django serves the SPA shell through a catch-all view that injects per-route head tags (title, meta description, canonical, Open Graph, JSON-LD) and a small <noscript> block with the main heading, summary and product list, read from the database.
Pre-render the static public routes (home, multivitamins hub, policies, about, contact) at build time (for example vite-plugin-prerender) so the full HTML is present without JavaScript.
Verify with curl (no JavaScript) that the HTML of a product page contains its title, description, price and JSON-LD.
Technical SEO checklist
Unique <title> (under 60 characters) and meta description (under 160) for every page, from seo_title and seo_description with a sensible fallback.
One <h1> per page, logical heading order, descriptive alt text, readable URLs (/multivitamins/daily-multivitamin-60-tablets).
Canonical URL on every page, filters and sort parameters canonicalized to the base listing.
robots.txt blocks /admin-panel, /api/, /cart, /checkout, /account; allows everything else and links the sitemap.
sitemap.xml generated from the database (products, categories, content pages) with lastmod, split if over 5,000 URLs.
Open Graph and Twitter card tags with an original share image per page type.
hreflang is not needed (single language and region); set lang="en" on <html>.
301 redirects for changed slugs. Trailing-slash policy is one consistent rule.
Core Web Vitals targets on mobile: LCP under 2.5 s, CLS under 0.1, INP under 200 ms. Use lazy loading, srcset, WebP, font preloading and code splitting by route.

9. Phase 7: bot detection and security
Prompt to agent
Implement layered bot protection. No single layer is enough, so each one adds to a risk score. A request above the block score is rejected, a request in the middle band gets a challenge, and everything is logged to BotEvent.
Layer
What to build
Honeypot field
A hidden, off-screen input (website) on register, login, contact, waitlist and checkout forms. Any value means bot: return a normal-looking success response and log it, so bots get no signal.
Time trap
The form carries a signed timestamp. Submissions faster than 2 seconds after render are suspicious (add to the score), and tokens older than 2 hours are rejected.
Challenge
Cloudflare Turnstile (free, privacy friendly) on register, login after 3 failures, contact, waitlist and checkout. The server verifies the token with the secret key on every protected POST. Make it configurable so tests can use the official Turnstile test keys.
Rate limiting
DRF throttles per IP and per account. Defaults: login 5 per minute, register 5 per hour, coupon check 10 per minute, order placement 5 per 10 minutes, contact 3 per hour, waitlist 10 per minute, anonymous API 100 per minute. Return 429 with Retry-After.
Account lockout
5 failed logins on one email locks it for 15 minutes with an email notice. Use identical error messages for unknown email and wrong password.
Header and UA checks
Add score for empty or known-automation user agents (curl, python-requests, headless markers), missing Accept-Language, and impossible header combinations. Allow-list real search engine bots verified by reverse DNS.
Behaviour signals
Add score for many different coupon codes tried quickly (coupon guessing), many accounts created from one IP, many carts created without browsing, and repeated failed checkouts.
IP controls
Admin-managed block list, automatic temporary block (1 hour) for repeat offenders, and X-Forwarded-For handled correctly behind the proxy.
Scraping defence
Throttle product list and detail endpoints per IP, and no sequential public IDs (use slugs and order numbers with a random part).
Other security requirements
Passwords hashed with Argon2, Django password validators on.
SECURE_SSL_REDIRECT, HSTS, SESSION_COOKIE_SECURE, CSRF_COOKIE_SECURE, SameSite=Lax, X_FRAME_OPTIONS=DENY.
Content Security Policy that allows only the site, Turnstile and self-hosted assets.
Strict CORS allow-list. No wildcard.
All queries via the ORM, all output escaped by React, no dangerouslySetInnerHTML except sanitized policy content.
Object-level permission checks: a user can only read their own orders and addresses.
File uploads validated for type, size and content.
pip-audit and npm audit clean of high and critical issues before release.
Logs never contain passwords, tokens or full phone numbers.
Acceptance: the bot tests in Phase 9 all pass, and a scripted bot run (section 12) is blocked or challenged at a rate of 95% or more while the 100 normal users are blocked at 0%.
